# Phase 1B sensitivity study (synthetic)

**Scope: SYNTHETIC inputs, SIMULATED frequency decisions, MODELLED energy.** No Linux
observation, no hardware actuation and no measured power are in this folder.

Generated by `python -m benchmark.sensitivity --outdir evidence/phase1b_sensitivity` at
the clean commit recorded in `PROVENANCE.json`, with all seeds and parameters. `SHA256SUMS`
covers every generated file plus `PROVENANCE.json` (not this README or itself). The
folder is marked `-text` in `.gitattributes`, so bytes match on every checkout. Verify:

```bash
cd evidence/phase1b_sensitivity && sha256sum -c SHA256SUMS
```

## How the inputs were made

K sweep: `monitor.synthetic.source` unchanged (1 s ticks, one CPU). `archived_seed11` is
exactly the Review 1 scenario; at K=3 it reproduces the archived `ours` result (transitions
at ticks 13/23/29, 1336.622 J). Other scenarios vary the seed, noise (0.3), phase length,
1–5 tick CPU bursts on idle, 1–5 tick idle dips inside CPU work, and 2-tick CPU/idle
flapping.

Interval sweep: a separate generator in `benchmark/sensitivity.py` builds float cumulative
counters every 0.1 s (four CPUs, same profile shares and jitter model as
`monitor.synthetic`) and differences them through the existing
`monitor.reader.compute_signals` at each interval. Runnable/blocked counts are the gauge
value at the window end, as on Linux.

## Metric definitions

- **transitions**: adjacent ticks whose applied simulated frequency differs.
- **appropriate frequency**: the policy's own class target for the scenario's true phase
  label (cpu→cpu_bound, io/io_burst→io_bound, idle, mixed).
- **lag (ticks)**: for a change into a sustained phase (> 5 ticks) whose target differs from
  the previous phase and from the frequency already applied, ticks from the phase's first
  tick to the first tick at the target. `unserved_changes`: target never reached in the phase.
- **frac_at_appropriate**: share of ticks whose applied frequency equals the appropriate one.
- **bursts_suppressed / bursts_total**: phases of ≤ 5 ticks whose target differs from the
  phase before; suppressed means the applied frequency did not change during the burst.
- **classifier_agreement**: share of ticks whose rule-based class matches the true label.
- **energy_j**: existing model, P = 21.6 + 32.4·(f/5.1 GHz)³·util/100 W, summed per interval.
- Interval sweep **class lag (s)**: from a sustained (≥ 10 s) phase change to the end of the
  first window classified as the new class. **Applied lag (K=3)**: to the end of the first
  window at the new target. A burst is **missed** when no window overlapping it is
  classified cpu_bound.

## Limits on interpretation

- The inputs are invented; the classifier rules and thresholds are provisional and were
  not tuned on these traces.
- Replay is open loop: running CPU-bound work at a lower frequency does not stretch it.
  So higher K can show *lower* model energy on bursty scenarios (bursts run at the low
  frequency) while `frac_at_appropriate` drops. That is a performance cost the model cannot
  price, not a saving.
- Burst detection depends on where bursts fall relative to window boundaries; the burst
  start times are fixed in `PROVENANCE.json`.
- These results describe the policy's response dynamics on synthetic data only. They are
  not measured energy, accuracy or completion-time evidence.
